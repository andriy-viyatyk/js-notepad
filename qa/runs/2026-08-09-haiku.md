## Details

### 1.2 markdown preview — PASS
Haiku called `create_page` with `editor: "md-view"`, `language: "markdown"` directly — did not
fall into the documented `plaintext` trap. Content was valid markdown; rendered correctly.
2 tool calls, ~25 s.

### 1.9 graph, first attempt — HARNESS FAIL (not a docs failure)
Haiku ignored persephone and built an SVG diagram via **Write + Artifact** (published a private
artifact). Root cause: the skill's rules banned Read/Grep/Glob/Bash but not Write/Artifact, and
the fork does not hard-enforce `allowed-tools`. Fixed the skill contract: "Use ONLY
mcp__persephone__* tools; every deliverable is a persephone page / ui_push output." Re-ran —
see below. Lesson recorded because any fork-based test harness has this hole: **constrain by
explicit rule, not just by tool allow-list.**

### 1.9 graph, second attempt — PARTIAL
With the fixed skill contract, Haiku created a valid `mermaid-view` page (subgraph for the
Fulfillment group, correct edges). Functionally right, but the test expected the force-graph
editor; "create a graph" is genuinely ambiguous between mermaid and force-graph for an agent
that hasn't read the overview. Not treated as a docs defect — the explicit-phrasing case is
covered by test 4.13.

### 4.13 force-graph explicit — PASS (minor deduction)
Request said "force-graph page" → Haiku read `read_guide("graph")` before creating, produced
`isGroup: true` + group-membership links + a `legend` block and tuned force options — all of
which live only in graph.md now, so the pages→graph pointer chain works end to end. Only miss:
title lacked the `.fg.json` suffix (page renders, but the JSON/Graph switch button is absent).
4 tool calls, ~33 s.

### 1.14 standalone refusal — PASS
Haiku attempted the impossible request, received the standalone-editor error with its hint,
recovered via `open_url` (capturing the returned `pageId`), and explained to the user that
browser-view is not a creatable editor. 8 tool calls — the recovery loop cost a few extra calls
but converged. Bonus finding while cleaning up: `closePage()` on a modified page blocks on the
"Unsaved Changes" dialog → `Request timeout` on the MCP call; documented in scripting.md.

### 2.5 ui_push grid — PASS (with an implementation-leniency nuance)
Grid rendered correctly in the Log View (verified via app snapshot: title + 4 columns × 5
rows). Nuance: Haiku sent `{ type: "output.grid", data: [...] }` — a shape the guide does not
document (`content` string + `contentType` is the contract) — and the handler accepted it.
Decision: keep the guide strict; an agent following the docs is always correct, and the
lenient path staying unadvertised costs nothing.

### 3.3 transform content — PASS
Haiku read the active page (`get_active_page`), sorted the array correctly, and wrote back via
`set_page_content` — it chose the tool path over `execute_script`, which is a legitimate
solution for this task. Cleanup note: the modified page closed without an Unsaved Changes
prompt this run (unlike the rest-client page earlier), so dirty-close prompting appears
content-host dependent — not worth documenting as a guarantee either way.

### 4.12 overview entry point — PASS
Cold-start request ("you've never used persephone"). Haiku's first tool call was
`read_guide("overview")` — the pointer in the read_guide description works — then it followed
the overview's routing to the scripting and boards guides, and delivered the summary through
`ui_push` (the overview's designated output channel). The 5 bullets matched the actual
mental model (editors, scripting, browser automation, boards, tools registry). 13 tool calls,
~77 s — the exploratory cost the overview was designed to bound.

### 5.1 open URL + heading — PASS
Preparation made the AVGridBoard page active, so an untargeted snapshot would have hit the
board (the Desktop reviewer's original stumble). Haiku: `open_url` → captured the returned
`pageId` → `browser_evaluate({ pageId, ... })` → "Example Domain". 6 tool calls, ~28 s. The
`open_url` pageId return + the "always pass pageId" guidance close this failure mode.

### 5.6 app window tabs — PARTIAL
First run (vague phrasing, "look at the persephone application window"): Haiku made 6 calls,
got confused about invoking deferred MCP tool schemas in the forked context, and ended by
asking the user for help. Second run (phrasing named the mechanism, `pageId: "app"`): clean —
`list_pages` + `browser_take_screenshot`, all 7 tabs reported with correct pinned/unpinned and
active state. Reading: the `pageId: "app"` capability is documented and usable once the agent
knows it exists, but a cold Haiku doesn't reliably *reach* for it from a vague request — partly
a deferred-tool-loading quirk of the fork harness, partly discoverability. Not treated as a
docs defect; noted for a future look at how browser tools surface in the fork.

## Summary

**9 tests: 7 PASS, 2 PARTIAL, 0 docs failures.** Every guide-gated behavior worked on Haiku:
read-before-create for notebook/graph/rest-client, overview as cold-start entry point,
pageId capture from open_url, recovery from the standalone-editor error. The two PARTIALs are
an ambiguous-phrasing case (mermaid vs force-graph for "create a graph") and the app-window
discoverability case above. One genuine harness hole was found and fixed mid-run (the skill
could use Write/Artifact — contract tightened to persephone-tools-only). Two incidental
findings fed back into the docs: the `closePage` unsaved-dialog timeout (added to
scripting.md) and the undocumented `output.grid` `data`-array leniency (docs deliberately kept
strict).
