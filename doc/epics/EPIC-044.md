# EPIC-044: Board Secondary Views — boards that contribute a synchronized sidebar view

**Revision note (US-852 / D3).** The shared-state channel was implemented with **round-trip-through-host + a monotonic `sharedStateSeq` guard** instead of the originally-sketched `lastWriterFrameId` echo-suppression + optimistic-apply. **Follows:** [EPIC-042 — Boards as Custom Editors](EPIC-042.md) and [EPIC-043 — Content-Host Boards](completed.md#epic-043). This epic adds the last missing piece that keeps built-in editors from moving out to boards: an editor's **secondary (sidebar) view**.

## The big idea

Boards can now be full custom editors (EPIC-042) that own Persephone's content host (EPIC-043). The remaining gap: several built-in editors — **Todo** foremost — contribute a **secondary view**, a sidebar panel wired to the same model as the main view. A board today has **one** iframe (the main view) and no way to put a second, coordinated surface in the sidebar.

This epic lets a board declare a **secondary view**: a second board-relative `.html` file rendered in an **additional iframe** inside a sidebar panel. The two frames stay synchronized through a new **shared-state channel** injected into every board frame:

```js
persephone.state.init(                                // declare defaults + which keys persist
  { selected: null, filter: "all", scratch: {} },
  { restorableKeys: ["selected", "filter"] },         // ONLY these are saved to the page descriptor
);
const s   = await persephone.state.get();             // current shared state (object)
persephone.state.set({ selected: "work" });           // replace shared state
persephone.state.merge({ filter: "open" });            // shallow-merge keys
const off = persephone.state.onChange((s) => { … });   // react to any frame's change
```

Plus a control any frame uses to declare/replace the board's set of secondary views at runtime:

```js
persephone.setSecondaryViews([                        // replace the full set of sidebar panels
  { id: "lists",  html: "lists.html",  title: "Lists"  },
  { id: "detail", html: "detail.html", title: "Detail" },
]);
persephone.setSecondaryViews([]);                     // remove all secondary views
```

**Why the shape is different from a built-in editor.** A built-in editor shares state because the main React view and the secondary React view are two components over **one model instance** (the Todo panel calls `model.setSelectedList()`, the main body re-reads `state.filteredItems`). A **sandboxed board cannot import a React component** or touch the model directly — so the "shared model" becomes a **shared-state object** owned by the Persephone-side board model and mirrored into every board frame over the existing renderer↔iframe channel. This is a faithful analogue: the board model *is* the single model; `persephone.state.*` is how the frames read and write it.

**Why it matters.** This is the enabling plumbing for migrating built-in editors (Todo, and later others) out of Persephone's core and into boards — the long-stated goal of EPIC-042/043. Todo's main list + its "Lists / Tags" sidebar panel + the selection→filter coupling map exactly onto: main iframe + secondary iframe + `persephone.state.*`.

## Scope

**In scope:**
- A manifest declaration (`secondaryViews`) — an array of view decls (`{ id, html?, title?, icon? }`) that light up sidebar panels for the board (independent of any file association).
- A **shared-state channel**: `persephone.state.init/get/set/merge/onChange`, injected into **all** board frames (main and secondary), authoritative on the Persephone side. **Opt-in persistence** — only keys a board declares via `state.init(defaults, { restorableKeys })` are saved in the page descriptor (so large/transient state never bloats the open-pages file); declared keys survive restart and reload.
- **Multiple** secondary views per board, each hosted in its own sidebar panel via a stable panel-id family `board-secondary:<viewId>`, reusing the existing `BoardWebview` / `board://` / port-handshake machinery (parametrized by entry file). Persephone already renders multiple panels per editor (the Link editor contributes three), so this is the natural fit.
- `persephone.setSecondaryViews([...])` so a frame can declare/replace the board's set of secondary views at runtime (each: `{ id, html?, title?, icon? }`).
- Persistence & restore of the declared (restorable) shared-state keys and the declared secondary views.
- A **proving-ground Todo board** — the built-in Todo reimplemented as a content-host board with secondary views (coordinated via `persephone.state.*` + `persephone.host.*`), registered **alongside** the built-in Todo for A/B testing. The built-in editor is **not** removed.

**Out of scope:**
- **Removing** the built-in Todo editor (or migrating any other editor). This epic *adds* a Todo board as the proof and keeps the built-in editor; removal is a later task gated behind a separate follow-up epic (to be described after this one ships).
- Non-sidebar layouts (bottom panels, split main), and any new theming/token surface — the secondary iframes reuse the same `--p-*` contract and CSP.
- A **promote-to-main** ("show in main view") affordance for board secondary views — the `SideBarPanelHeader` supports it, but a board secondary view is a distinct HTML entry, not the main board, so promotion semantics are deferred.
- **Keeping a board alive on the page via its secondary views** (Pattern B survival). Board panels die on navigate-away and the board is disposed (D8); a "keep the board as a sidebar contributor" mode is a future task/epic.
- Cross-board shared state — shared state is per board page (per model instance), never shared across pages or boards.

## Recommended architecture

Reuse everything; add three small seams. The investigation (secondary-view registry, board bridge, board model/persistence) confirmed all the load-bearing pieces already exist:

**Canonical field names** (the doc was edited across turns — these are authoritative; the review flagged the `secondaryView`/`secondaryViews` singular-vs-plural footgun, so the state metadata field is deliberately renamed):
- Manifest: **`secondaryViews: SecondaryViewDecl[]`**, where `SecondaryViewDecl = { id: string; html?: string; title?: string; icon?: string }`.
- Model state: **`secondaryViewDefs?: SecondaryViewDecl[]`** — the runtime set (seeded from the manifest, or replaced via `setSecondaryViews`).
- Model state (existing base field): **`secondaryView?: string[]`** — the *derived* panel-id list the shell reads (`secondaryViewDefs.map(d => "board-secondary:" + d.id)`).
- Model state: **`sharedState?: Record<string, unknown>`** (full, in-memory) + **`sharedStateRestorableKeys?: string[]`** (declared via `state.init`).

1. **Declare** — an editor contributes sidebar panels via `state.secondaryView: string[]` (bare panel ids); `contributesPanels()` gates rendering. **`BoardEditorState.secondaryView` already exists but is never populated.** We populate it with **one id per declared secondary view** using the stable id scheme `board-secondary:<viewId>`, derived from `state.secondaryViewDefs` (seeded from manifest `secondaryViews` and/or runtime `setSecondaryViews`).

2. **Render** — teach `secondary-view-registry` to resolve the whole `board-secondary:*` id family to a **single generic `BoardSecondaryView` component** (prefix-aware `has()`/`get()`), and add `panelId` to `SecondaryViewProps` so the component knows *which* view it is. It strips the prefix → view id → looks up the `state.secondaryViewDefs` entry, and renders a **`BoardWebview`** pointed at that view's HTML entry wrapped in a `SideBarPanelHeader` (title/icon from the decl). Every board panel gets the **same `BoardEditorModel` instance** via `SecondaryViewProps.model`, so all frames sit over one model — the single-model pattern, preserved.

3. **Synchronize** — mirror the **`persephone.host.*` precedent** exactly (the renderer↔iframe direct `postMessage` channel, *not* the main `MessagePort`). The board model holds the shared state in its own `TComponentState` (`state.sharedState`); each `BoardWebview` instance is a per-frame sync bridge — it seeds its frame on load, pushes `state:sync` on change (echo-guarded by originating **frame id**, robust under `merge` where value-equality is not), and applies inbound `board:setState`/`board:mergeState` to the model. **Persistence is opt-in** (not free): the base `BoardEditorModel.getRestoreData()` writes only `pick(sharedState, sharedStateRestorableKeys)` into `EditorDescriptor.state` — declared keys only, nothing if none declared — so a board can hold large/transient state in `sharedState` without bloating the open-pages file (concern raised in review). `secondaryViewDefs` (small) persists in full.

**Second iframe reuses `BoardWebview` — with an `isMain` role.** The `board://` protocol serves *any* file in the board folder with the same shim/boot/palette injection and CSP — a second `.html` needs **zero** protocol changes (confirmed). `BoardWebview` is parametrized by `{ model, boardRoot }` and hardcodes `index.html`; the changes are an `entry` prop (default `index.html`) and an **`isMain` prop** (default `true`). The `isMain` flag is load-bearing because the main and secondary frames share one `model.id`: **only the main frame** may call `model.setIframe`/`clearIframe` and `registerBoardFrame`/`unregisterBoardFrame` (else the last-mounted frame clobbers the main frame's automation target and CDP registration — see D7/B-fixes). Each frame still requests its own `MessagePort` (its own `boardId`), so `execute`/`readFile`/etc. work in every frame; both frames share the one model, hence the one shared state and (for content-host boards) the one content host. **Job reaping is reworked** so a secondary frame's port disposal reaps only its own sink (`boardId`), never the shared owner (`model.id`) — only `BoardEditorModel.dispose()` reaps the whole owner (see US-853).

## Design decisions (recommendations — confirm in review)

- **D1 — Shared state lives on `BoardEditorState.sharedState`, on the base `BoardEditorModel`, not a separate store.** Reuse the base model's existing `TComponentState`; get/set/merge operate on `state.sharedState`; frames subscribe via `state.use(s => s.sharedState)`. Because it is on the base model, *every* board (plain and custom-editor, `BoardContentEditorModel` included) gets shared state + secondary views (O1). No new store. Persistence is **opt-in** per key (D9), not automatic.
- **D2 — `persephone.state.*` is always available for every board** (no boot gate). Unlike `host.*` (needs a content host), shared state is a harmless in-memory object; gating buys nothing. `get()` mirrors `host.getContent()` (await-first-snapshot, then cached); `onChange` mirrors `onContentChange`.
- **D3 — Renderer is the single source of truth; writes round-trip through the host to every frame, seq-guarded (revised in US-852 implementation).** On a frame's `init`/`set`/`merge`, that frame's `BoardWebview` writes the shared model; **every** `BoardWebview` (including the originator's) then pushes `state:sync` to its own frame, each push stamped with a **monotonic `model.sharedStateSeq`**. The shim keeps a pure replica and applies a push only when its `seq` exceeds the last applied, so seed-on-load vs `init`/`set`/`merge` deliveries are order-independent. **This replaces the originally-sketched `lastWriterFrameId` echo-suppression + optimistic-apply** (see revision note below): there is no feedback loop to suppress (`state:sync` never re-posts), and suppression combined with a seed-on-load push created an init-clobber ordering hazard that the `seq` guard removes cleanly — and `seq` is robust under `merge` (the property value-equality lacked). Trade-off: the writing frame observes its own change after a sub-millisecond renderer round-trip rather than synchronously; `onChange` is the source of truth (React-`setState` semantics).
- **D4 — Second iframe = `BoardWebview` + an `entry` prop** (default `index.html`). Reuses host registration, port handshake, theme, CSP, content-host content sync. The secondary frame gets its **own** `MessagePort` (own `boardId`) but **shares the model** (hence shared state + content host).
- **D5 — Multiple secondary views via a `board-secondary:<viewId>` id family (no fixed cap).** A board contributes zero-or-more sidebar panels; each declared view maps to a stable panel id `board-secondary:<viewId>` (composite key `<editorId>::board-secondary:<viewId>` stays unique and restore-stable). The registry resolves the family to one generic component (prefix-aware), and `SecondaryViewProps` gains `panelId` (backward-compatible — existing panels ignore it). This mirrors how the Link editor already contributes three panels — the shell iterates `(model, panelId)` pairs unchanged.
- **D6 — Declared statically in the manifest and/or dynamically via `setSecondaryViews`.** Manifest `secondaryViews: [...]` seeds the set at open; `persephone.setSecondaryViews([...])` replaces it at runtime. Both write `state.secondaryViewDefs` (the metadata array) on the model, from which `state.secondaryView` (the derived panel-id list the shell reads) is recomputed. Each view decl is `{ id, html?, title?, icon? }`; `html` defaults to the main entry (`index.html`), and the frame's role reaches the board as `persephone.view` (`"main"` or the view `id`) via a `view=` URL query param the shim reads synchronously at boot (O6). View ids are author-supplied — reject/normalize ids containing `::` (the composite-key separator) at the `setSecondaryViews`/manifest-read boundary.
- **D7 — Automation targets the main frame only (v1), via an `isMain` frame role.** Because the main and secondary `BoardWebview`s share one `model.id`, the **secondary frame must NOT** call `model.setIframe`/`clearIframe` or `registerBoardFrame`/`unregisterBoardFrame` — otherwise the last-mounted frame clobbers the shared `currentIframe` and the single CDP registration keyed on `model.id`, so `browser_*` would drive the wrong frame and a secondary unmount would break main-frame automation entirely (independent-review B2/B3, verified against `BoardWebview.tsx`, `controller.ts`, `cdp-service.ts`, `BoardTargetModel.ts`). The new `isMain` prop (default `true`) gates all three calls; only the main frame owns them. Driving the secondary frame from automation is deferred.
- **D8 — Board secondary views die on navigate-away (Pattern A), not Pattern B survival.** A board that contributes panels is **not** kept alive as a sidebar-panel contributor when the user navigates its main view away — its secondary views are removed and the board is disposed normally. Concretely: the base `EditorModel.beforeNavigateAway` already clears `state.secondaryView` (so `contributesPanels()` → false before the demotion/dispose decision), so the base board **does not override** `beforeNavigateAway`/`survivesNavigation` for panels. (This is orthogonal to the existing *busy*-process retention for plain boards, US-799, which is unchanged.) Keeping a board alive on the page via its secondary views is explicitly a **future task/epic** — not needed now.
- **D9 — Shared-state persistence is opt-in per key via `state.init(defaults, { restorableKeys })`.** Saving all of `sharedState` unconditionally could bloat the open-pages JSON if a board stashes large/transient data (concern raised in review). Instead a board declares its defaults and the subset of keys that should survive restart/reload; `init` seeds defaults (fill-missing — restored values win) and records `restorableKeys` on the model. The base `getRestoreData()` persists only `pick(sharedState, restorableKeys)` (nothing if a board never calls `init`/declares no keys). `init` is idempotent; typically the main view calls it once (last `init` wins for the key set).
- **D10 — Multi-frame job reaping is per-sink, not per-owner.** Each frame mints its own port (own `boardId`) but shares `ownerId = model.id`. An ordinary `disposeBoardPort(boardId)` (a secondary panel closing, a single-frame remount) must reap only that sink; the whole owner is reaped only from `BoardEditorModel.dispose()` (page close). Without this, a secondary frame's teardown tree-kills the main frame's spawned processes (independent-review B1, verified against `board-bridge.ts` `disposeBoardPort`/`reapBoardOwner`). Owned by US-853.

## Concerns / open questions (need user input)

- **O1 — Secondary view without a file association.** ✅ **Resolved (2026-07-15):** secondary-view **and** shared-state are **general board functionality**, implemented on the **base `BoardEditorModel`** — available to *every* board (plain `board-view` opened via `persephone-board://`, and custom-editor `board-editor:<root>` boards alike); `BoardContentEditorModel` inherits both for free. Consequently the `secondaryView` manifest field is read by a **separate reader independent of `getBoardEditorAssociation`** (which stays `fileMasks`-gated for the *custom-editor* axis only), and the shared-state store + `persephone.state.*` wiring sit on the base model, not on any file-editor path.
- **O2 — `persephone.state.*` on plain boards too, or content-host only?** ✅ **Resolved (2026-07-15):** shared state is available to **all kinds of boards** (no gate) — it lives on the base `BoardEditorModel` (O1/D1/D2).
- **O3 — Should the secondary frame receive `host:content`?** ✅ **Resolved (2026-07-15):** yes — `persephone.host.*` is available in **all** views (main and secondary), since both frames share the one content host on the shared model. Concurrent writes are the board author's concern (same as two Monaco split-views). US-853 must verify the content-host content sync runs in the secondary frame too, not just the main one.
- **O4 — `get()` semantics.** ✅ **Resolved (2026-07-15):** mirror `host.getContent()` — `get()` returns a Promise resolving to the first synced snapshot, then resolves immediately with the cached value thereafter; reactive reads use `onChange`.
- **O5 — One secondary view vs many.** ✅ **Resolved (2026-07-15):** support **many** — general and flexible, matching that Persephone already renders multiple panels per editor (the Link editor contributes three). Each declared view is a stable panel id `board-secondary:<viewId>`; the registry resolves the family to one generic component (prefix-aware, `SecondaryViewProps.panelId` added); the set is declared in the manifest (`secondaryViews`) and/or replaced at runtime via `persephone.setSecondaryViews([...])`. No fixed cap.
- **O6 — A single HTML that knows its role.** ✅ **Resolved (2026-07-15):** expose `persephone.view` = `"main"` for the main frame, or the **view's `id`** (from `secondaryViews` / `setSecondaryViews`) for a secondary frame — so one HTML file can encapsulate every view and branch on `persephone.view` to render each. Delivered **synchronously at boot** via a `view=<role>` **URL query param** on the iframe `src` (alongside the existing `?v=<boardId>` nonce), which the shim reads from `location.search` before any author script runs — no async wait. Consequently a view decl's `html` is **optional**, defaulting to the main entry (`index.html`): a board can point every view at one file and switch on `persephone.view`, or give each view a distinct `.html`.
- **O8 — Unbounded shared-state persistence bloating the open-pages file.** ✅ **Resolved (2026-07-15):** persistence is **opt-in** — a board declares defaults and the restorable subset via `persephone.state.init(defaults, { restorableKeys })`; only those keys are written to the descriptor (D9). Nothing persists if a board never declares keys.
- **O7 — Scope of the proving ground.** ✅ **Resolved (2026-07-15):** the proving ground is a real **Todo board** — the built-in Todo editor reimplemented as a content-host board with secondary views (main list + a Lists/Tags panel coordinated via `persephone.state.*`, content via `persephone.host.*`), registered for the same Todo file type. The **built-in Todo editor stays**: with both registered, the switch offers two Todo editors, which is the intended A/B test surface. Removing the built-in Todo is a **separate later task**, which the user will gate behind **one more epic** (to be described after this epic ships).

## Acceptance criteria

- A board can declare one or more secondary views in `board-manifest.json`; opening it shows a synchronized iframe per view in its own sidebar panel with the declared title/icon.
- `persephone.state.init/get/set/merge/onChange` work from **all** frames (main + every secondary); a change in one frame is observed in the others; state is authoritative on the Persephone side.
- **Opt-in persistence:** only keys declared via `state.init(defaults, { restorableKeys })` are written to the page descriptor; undeclared/transient state is never persisted (no open-pages bloat).
- `persephone.setSecondaryViews([...])` declares/replaces the board's set of secondary views at runtime from any frame (attaching/detaching panels live); `[]` removes them all.
- Navigating the board's main view away removes its secondary views and disposes the board (Pattern A) — it is not kept alive as a sidebar contributor.
- A secondary panel closing/unmounting never kills the main frame's spawned processes and never breaks main-frame automation (per-sink reaping + `isMain`-gated CDP/iframe registration).
- The declared (restorable) shared-state keys and the declared secondary views **survive app restart** (both plain and content-host boards) and **board reload** (`reloadToken`).
- The proving-ground **Todo board** reproduces the built-in Todo's main-list + Lists/Tags-panel coordination via `persephone.state.*` (+ content via `persephone.host.*`), registered alongside the built-in (two Todo editors in the switch), user-verified end-to-end; selection survives restart and reload.
- Developer + user + board-author docs updated; the demo board showcases the surface. No architecture/standards violations at epic review.
