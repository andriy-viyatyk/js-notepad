## Goal

Reach a sustainable lint baseline:

- **Zero errors** — CI/lint never has a hard failure.
- **Zero unreviewed warnings** — every remaining warning is either fixed, intentionally suppressed (with a comment explaining why), or its rule is disabled with a documented rationale.

This is **phased**. Each phase ends with a checkpoint where the user reviews progress before the next phase starts.

### 2.2 `import/no-duplicates` (10 occurrences)

Same module imported twice in one file — e.g., `import type { X } from "react"; import { useState } from "react";` could be merged. Often `--fix` handles these. The Tooltip.tsx file shows `'D:\...react\index.js' imported multiple times`. Mechanical merge; no behavior change.

### 2.3 `import/no-named-as-default` (10 occurrences)

All `clsx`-related: `import clsx from "clsx"` triggers this because `clsx` package exports `{ clsx }` as named but no default. The fix is `import { clsx } from "clsx"`. ~10 files; mechanical. Affected files (per Phase-0 audit): `HeaderCell.tsx`, `SelectColumn.tsx`, `FilterBar.tsx`, `FocusModel.tsx`, and ~6 others — re-grep after Phase 1 lands since file list may differ.

### 2.4 `@typescript-eslint/no-unused-vars` (77 occurrences)

Three sub-patterns. Triage by category:

- **Truly dead** — remove the declaration. Probably the majority.
- **Intentionally unused parameter** (e.g., a callback signature you don't need but the type requires) — prefix with `_` (the rule allows that by default; if it doesn't here, configure `"argsIgnorePattern": "^_"`).
- **Unused but kept for documentation/future** — prefix with `_` or add `// eslint-disable-next-line @typescript-eslint/no-unused-vars` with a comment saying why.

77 cases is too many to enumerate up front. Strategy: do them in a single pass, file by file, presenting a summary diff for review before commit.

## Concerns / Open questions

1. **Will Phase 1 surface new warnings?** Adding `plugin:react-hooks/recommended` activates ~14 `exhaustive-deps` warnings that today appear as "rule not found" errors. Net effect on the counter: -7 errors, no new warnings beyond what's already counted. Confirmed.

2. **What about the per-file `clsx` import — is the named-import form actually correct?** `clsx`'s `package.json` typically exports both a default and named — `import clsx from "clsx"` works at runtime but the linter prefers `import { clsx }` because of the named-as-default convention. Worth a quick smoke test (`import { clsx } from "clsx"; clsx("a", "b")`) before bulk-rewriting. If the runtime shape differs, fall back to per-file disable.

3. **Do we want CI enforcement?** Today `npm run lint` is run by hand. If we want this baseline to stick, a pre-commit hook or CI step would enforce zero errors. Out of scope for US-588 unless explicitly requested — flag for backlog.

4. **`react-hooks/recommended` includes other rules besides `exhaustive-deps` (e.g., `rules-of-hooks`).** These may surface additional errors after Phase 1. If so, fold the fixes into Phase 1 or split into a sub-phase.

5. **Should warnings ever become errors?** Some projects elevate selected warnings to errors after baseline cleanup, to prevent regression. Not in initial scope but worth discussing after Phase 3.
